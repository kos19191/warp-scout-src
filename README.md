# WarpScout

Android-приложение для работы через Cloudflare WARP. Оно само находит в вашей сети адрес
Cloudflare, который пропускает трафик, поднимает на нём туннель и держит его — без ручного
перебора адресов, без сторонних VPN-библиотек и без сервера-посредника.

Проект не аффилирован с Cloudflare. Это клиент, который реализует протокол сам: обмен ключами,
handshake, сессии, пересогласование, разбор пакетов, маршрутизацию. Всё, с чем приложение
разговаривает, — это адреса Cloudflare и ваш телефон.

---

## Что делает приложение

- **Два вида экрана.** Упрощённый — одна большая кнопка «включить/выключить», проверка связи
  и резервная точка; расширенный — все вкладки: подбор, настройки, приложения, журнал. Переключает
  еле заметный тумблер внизу экрана, выбор запоминается. Тема — светлая, тёмная или как в системе
  («Настройки» → «Тема оформления»).
- **Подбирает рабочую точку входа.** Перебирает адреса и порты Cloudflare WARP, проверяет их
  настоящим handshake, а не пингом, и оставляет те, что ответили именно вашему ключу.
- **Поднимает туннель само.** Свой `VpnService`: WireGuard/AmneziaWG внутри приложения,
  без внешних библиотек. Подключение — одно нажатие, при обрыве поднимается заново без вас.
- **Меняет точку, когда прежняя умерла.** Держит очередь проверенных адресов и переходит на
  следующий сам — в том числе ночью, когда никто не нажимает кнопок.
- **Показывает, что реально открывается.** Прогоняет список сайтов из-под туннеля и говорит
  «открылось / не открылось», а не «подключено, наверное, работает».
- **«Подключено» значит «данные ходят».** После подъёма, при открытии экрана и когда приложения
  шлют пакеты без ответа, сервис проверяет связь запросом через сам туннель: Cloudflare по IP
  (заодно видно, через WARP ли ушёл запрос и откуда виден выход) и TCP-соединение с сервером
  Telegram. Два провала подряд — туннель переподключается сам.
- **Резервная точка.** Её выбирают из лучших точек последнего подбора (у каждой видно, что о ней
  знает фоновая проверка: «отвечает» или «не ответила в 12:53»). Если текущая замолчит, туннель
  перейдёт на резервную первой. «Подключить» сначала проверяет точку рядом с работающим туннелем и
  не гасит его, если точка молчит.
- **Возвращается сам после перезагрузки и обновления** — если перед этим туннель был включён и его
  не выключали вручную. Выключенный руками (кнопка, плитка, уведомление) туннель сам не включается.
- **Умеет отправить часть трафика в свою страну.** WARP — anycast, страну выхода выбрать нельзя;
  для отдельных сайтов можно добавить свой WireGuard/AmneziaWG-сервер.
- **Разделяет трафик.** По приложениям и по адресам: всё в туннель, только выбранные, всё кроме
  выбранных.
- **Объясняет отказы по-русски.** В журнале видно каждый шаг с временем и длительностью, и что
  делать, если не поднялось. «Выгрузить журнал в .txt» (вкладка «Журнал») сохраняет журнал
  целиком в «Загрузки» и сразу открывает «Поделиться»: с версией и номером сборки, телефоном,
  состоянием сервиса, последним подбором и падениями. «Скопировать журнал» по-прежнему кладёт в
  буфер обмена только хвост — длинный текст режут и буфер, и мессенджеры.
- **Показывает, сколько туннель уже работает.** Время считается от подъёма сессии, а не от
  открытия экрана, — часы работы видно и после перезапуска приложения. Журнал открывается на самых
  свежих строках и листается, разделы переключаются кнопками снизу или смахиванием влево-вправо.

## Как это работает

### 1. Подбор точки входа

Cloudflare WARP отвечает на любой из своих anycast-адресов, но в каждой сети часть адресов и
портов закрыта. Приложение перебирает их и проверяет по-настоящему.

**Что перебирается:**

- подсети Cloudflare WARP: `162.159.192.*`, `162.159.195.*`, `8.6.112.*`, `8.34.70.*`,
  `8.34.146.*`, `8.35.211.*`, `8.39.125.*`, `8.39.204.*`, `8.39.214.*`, `8.47.69.*`,
  `188.114.96.*`…`188.114.99.*`, плюс имя `engage.cloudflareclient.com`;
- октеты `1…10` внутри подсети (не весь /24: разницы в поведении нет, а скан в 25 раз короче);
- порты из документации WARP: 500, 854, 859, 864, 878, 880, 890, 891, 894, 903, 908, 928, 934,
  939, 942, 943, 945, 946, 955, 968, 987, 988, 1002, 1010, 1014, 1018, 1070, 1074, 1180, 1387,
  1701, 2408, 2506, 3138, 3476, 3581, 3854, 4177, 4198, 4233, 4500, 5279, 5956, 7103, 7152,
  7156, 7281, 7559, 8319, 8742, 8854, 8886;
- по умолчанию проверяется 120 адресов (`IP:порт`), максимум — 4000. Пул формируется
  расслоённой выборкой: каждая пара «подсеть × порт» получает свою долю, поэтому скан не
  скатывается в одну подсеть.

**Как проверяется точка.** Отправляется тот самый профиль мусора, который потом пойдёт в
работе, и следом handshake initiation (148 байт). Считается ответом handshake response (92 байта,
проверяются `receiver_index`, MAC1 и тег AEAD) или cookie reply — оба означают «сервер живой и
принимает наш ключ». Молчание и ICMP «порт закрыт» различаются: второе сразу говорит, что порт
закрыт, а не что сеть тормозит. Внутри одной пробы уходит 4 инициации с интервалом 450 мс —
первая датаграмма на мобильной сети теряется регулярно. Параллельно работают 48–64 сокета.

**Профили шума (AmneziaWG).** На каждой из лучших точек проверяется не один вариант, а все:
`none` (чистый WireGuard — на части сетей DPI его не трогает вовсе), `tls-fixed`, `quic:` под три
SNI из списка российских доменов, `sip`. Сравнивается результат, а не догадка.

**Финал подбора.** Десяток лучших точек поднимается настоящим туннелем, и изнутри по каждой
прогоняются проверки сайтов (см. ниже). Победитель выбирается по числу реально открывшихся
сайтов, и только потом по скорости и стабильности. В «Лучших конфигах» остаются три варианта на
разных адресах — переключение на запасной занимает одно нажатие.

На той же сети повторный подбор сначала проверяет прошлую рабочую точку: секунды вместо минут.
Полный скан запускается, только если она перестала работать.

### 2. Подключение

- **Куда подключается:** к найденной паре `адрес:порт` Cloudflare, по UDP. Никаких промежуточных
  серверов: трафик идёт от телефона прямо в ближайший узел Cloudflare.
- **Чем подключается:** собственным `VpnService`. X25519, ChaCha20-Poly1305, BLAKE2s и формат
  пакетов реализованы в проекте (`core/`), поэтому туннель работает без AmneziaVPN и без
  системного WireGuard.
- **Ключи WARP:** берутся через те же публичные зеркала, что использует генератор конфигов, и
  кешируются на телефоне; если зеркала недоступны — используется сохранённый аккаунт. Можно
  вставить и свой конфиг. Ключи не покидают устройство.
- **Параметры по умолчанию:** адрес в туннеле `172.16.0.2` (+ IPv6), MTU `1280`, DNS
  `1.1.1.1`/`1.0.0.1`, keepalive 25 с — всё меняется в настройках.
- **Если точка молчит:** при подключении перебирается до шести точек (выбранная → последняя
  рабочая → из подбора → запасные адреса Cloudflare).
- **Перебор можно отменить.** Пока он идёт, главная кнопка называется «Отменить подключение», а
  ход перебора виден строкой над ней. Выключение плиткой в шторке или «Отключить» в уведомлении
  тоже останавливает перебор: следующая точка не стартует, и туннель сам не включится.
- **Рукопожатие по стандарту.** Метка времени в инициации — TAI64N, как в WireGuard: каждая
  следующая строго новее прошлой. WARP её не проверяет, а свой сервер (WireGuard, AmneziaWG)
  проверяет и молча отбрасывает инициацию с меткой не новее прежней — до 1.10.26 из-за этого свой
  сервер второго выхода через несколько минут переставал пересогласовывать сессию.

### 3. Удержание туннеля

- **Keepalive** — по настройке (25 с по умолчанию), но с нижней границей: не реже 60 с при
  активном экране и не реже 90 с, когда экран погашен и трафика нет давно. Максимум — 120 с:
  дольше NAT всё равно не помнит соединение. `0` — выключен совсем.
- **Пересогласование сессии (rekey)** — каждые 150 с при живом трафике: протокол жёстко требует
  успеть до 180 с, иначе сервер выбрасывает сессию и снаружи это выглядит как «подключено, но
  Telegram пишет Соединение…». Неудачный rekey повторяется через 5 с.
- **Мёртвая сессия.** Если пересогласование не прошло, туннель переподнимается; если и это не
  вышло — берётся следующая точка из очереди (до шести смен подряд). Если не ответила ни одна,
  приложение не сдаётся и не оставляет мёртвый туннель висеть: новый круг — через растущую паузу
  (30 с, 1 мин, 2 мин, дальше раз в 5 минут, всего около 50 минут). Новая сеть или включённый
  экран запускают попытку сразу. Точки, которые просто промолчали, в «мёртвые» записываются,
  только если в том же круге поднялась другая: когда молчат все, дело обычно в сети.
- **Выключил сам — сам и включишь.** Кнопка «Выключить туннель», плитка в шторке и «Отключить» в
  уведомлении — это решение человека: после него приложение туннель само не включает — ни
  переподключением, ни фоновым подбором с авто-применением. Переподключается оно только тогда,
  когда туннель упал без вашего участия. Пока сервис держит туннель в ожидании повтора, кнопка и
  плитка показывают «Выключить» / «переподключается» — выключить можно в любой момент.
- **Один сервис — один туннель.** «Отключить» и сразу «Подключить» (так работает перебор точек)
  больше не порождают второй экземпляр сервиса. Раньше закрытый системой экземпляр мог жить
  дальше сам по себе: на каждую смену сети он поднимал свой туннель на том же ключе, сессии
  перебивали друг друга («сессия молчит» каждую минуту), и туннель отключался без возврата.
  Если система отзывает VPN (включили другой VPN), это теперь видно в журнале.
- **Смена сети** (Wi-Fi ↔ мобильные) — переподключение без участия пользователя. UDP-сокет
  привязан к маршруту, и после смены сети его обязательно надо открыть заново, иначе «туннель
  есть, трафика нет». События сети приходят пачкой, поэтому они склеиваются тихим окном 700 мс:
  переключение занимает 1–2 секунды, а не 5–8.
- **Память точки по сети.** Приложение запоминает, какой адрес работал на Wi-Fi, а какой — на
  мобильной: адреса Cloudflare не универсальны, и «живой дома» может закрывать порт на LTE.
  Поэтому после переключения оно сразу начинает с проверенного на такой сети адреса, а не с
  адреса из другой сети.
- **Готовность сети.** Пока система не признала сеть рабочей (только что включённый Wi-Fi ещё
  раздаёт адрес, портал проверки доступа не пройден), инициации не отправляются впустую: ждём до
  трёх секунд. Это и быстрее, и меньше расхода модема.
- **Провал не досиживают.** Если точка ответила «порт закрыт» или промолчала, переход к
  следующей происходит через доли секунды, а не через 15 секунд ожидания.
- **Дозор.** Пока туннель работает, раз в 12 минут приложение тихо проверяет две точки из
  очереди перебора — ту, на которую перейдёт при обрыве, и ещё одну по кругу: одна-две
  инициации handshake с отдельного сокета мимо туннеля. Текущую сессию это не трогает. Живая
  точка встаёт в перебор сразу за текущей, дважды промолчавшая или ответившая «порт закрыт»
  уходит в конец — при обрыве не тратится попытка на мёртвый адрес. Строка `дозор:` в журнале
  показывает итог каждого обхода. Если промолчали все проверенные точки, дозор пробует ещё и
  текущую точку с нового сокета: туннель на ней работает, и если с нового порта молчит и она,
  значит, сеть сейчас не пропускает новые соединения к WARP (так ведёт себя DPI), а точки ни при
  чём — их метки тогда не меняются, а в журнале так и написано.
- **Честный статус после обновления и перезагрузки.** Обновление приложения и перезагрузка
  телефона закрывают сервис туннеля. Экран это видит сразу (а не через две с половиной минуты, как
  раньше) и пишет причину. Если туннель перед этим работал и его не выключали вручную, он
  поднимается сам — на последней рабочей конфигурации; так же он ведёт себя, когда систему
  перезапускает сервис или включён «Постоянный VPN» в настройках Android. Шапка выгруженного
  журнала тоже проверяет, жив ли сервис, и показывает итог последней проверки связи.
- **Проверка точки до переключения.** Выбор из «лучших» сначала проверяется пробой рядом с
  работающим туннелем: если точка молчит, туннель не гаснет, а на экране так и написано — «не
  отвечает, оставил текущую». Отметки дозора («отвечает» / «не ответила в 12:53») видны в списке
  до нажатия.
- **Без пробуждений вхолостую.** Поток, читающий tun, спит в `poll()` до прихода пакета, а не
  просыпается каждые 20 мс проверить, нет ли данных.
- **Подбор возвращает туннель.** Перед замерами подбор гасит туннель (иначе мерит сам WARP), а
  по окончании поднимает его снова — при любом исходе: нашлась новая точка (тогда на ней),
  ничего не нашлось, подбор отменён или упал (тогда прежнее подключение).
- **«Остановить подбор» останавливает сразу.** Скан пула, проверки ресурсов и проверка изнутри
  прерываются за секунду-две, а недосчитанный результат не сохраняется и не применяется. Подбор
  переживает поворот экрана и возврат в приложение: новый экран показывает, что подбор идёт, и
  останавливает именно его. Кнопка видна только пока подбор идёт.
- **Долгая тишина.** Если сети нет 45 секунд, туннель снимается, чтобы трафик не уходил в
  пустоту, — но только когда сети действительно нет: проверка идёт по системному состоянию, а не
  по внутреннему флагу. И сразу после снятия приложение само проверяет раз в 15 секунд, не
  появилась ли сеть, — поднимает туннель без нажатий.

### 4. Что проверяется после подъёма

- **Сайты:** Google (`generate_204`), YouTube, ChatGPT, OpenAI API, Telegram web, Discord,
  WhatsApp web, X, Cloudflare trace — плюс контрольная проверка (`ru.wikipedia.org`), по которой
  видно, что сайт открывается вообще без туннеля.
- **Из-под туннеля:** `cloudflare.com/cdn-cgi/trace` с проверкой `warp=on` (значит, трафик
  действительно идёт через WARP) и `ipinfo.io` — какой адрес и страна видны снаружи.
- **DNS:** системный резолвер сверяется с двумя независимыми DoH (Cloudflare и Google). Если
  системный отдаёт адреса, которых нет ни в одном из них, — это подмена DNS, и приложение
  говорит об этом прямо, а не «сайт не открывается».
- **Регион выхода** через WARP определяется один раз после подъёма по `cdn-cgi/trace`
  (например, `HEL · RU`), чтобы было видно, куда именно ведёт текущий туннель.
- **Медиа Telegram** (с 1.10.34): проверка связи открывает соединение с сервером Telegram, но
  этого мало — фильтры пропускают соединение и режут поток. Поэтому раз в полчаса при включённом
  экране приложение загружает начало официального APK Telegram с telegram.org (до 256 КБ, по IPv4,
  как ходит сам Telegram) и смотрит на скорость и паузы. В журнале — строка `проверка Telegram:`
  (`медиа ✓`, `медиа тормозит`, `медиа рывками`, `медиа встаёт`), на экране — «Telegram: связь
  есть, медиа тормозит». Если сервер загрузки окажется не в сетях Telegram, вывод о медиа не
  делается — так и написано.
- **Скорость** замеряется через `speed.cloudflare.com`, если запустить замер из отчёта.

### 5. Второй выход: своя страна для отдельных сайтов

WARP — anycast: узел выбирает Cloudflare по вашей сети, страну выбрать нельзя. Если нужен
конкретный регион для конкретных сайтов, нужен свой сервер.

1. Поднимите WireGuard или AmneziaWG на любом VPS в нужной стране.
2. **Настройки → Второй выход (регион)**: вставьте клиентский конфиг, перечислите домены.
3. **«Собрать IP из доменов»** — домены развернутся в адреса через DoH (`/32` и `/128`).
4. **«Сохранить и применить»**.

Пакеты на эти адреса пойдут через ваш сервер, всё остальное — через WARP. Если сервер недоступен,
его подсети возвращаются в WARP: сайт работает, регион другой, туннель не рвётся. Ограничения:
сайты на общих CDN-адресах могут уйти не через тот выход; для Outline/Shadowsocks второй выход не
подходит — им нужен TCP-стек.

**Proton Free** (конфиг из аккаунта Proton): приложение само перебирает бесплатные серверы Proton.
При стране «Любая» сначала пробуются ближние страны — Нидерланды, Польша, Румыния, Швейцария (по
одному серверу), и только потом сервер из самого конфига и дальние страны (Канада, США, Япония,
Сингапур, Мексика). До 1.10.36 первым шёл сервер из конфига: у бесплатного конфига он бывает в
Мексике, и второй выход — а с ним и сайты через него — был заметно медленнее, чем мог бы. Выбранная
вручную страна по-прежнему идёт первой.

Если свой сервер перестал отвечать сразу после обновления до 1.10.26, перезапустите на нём
WireGuard/AmneziaWG (например, `systemctl restart wg-quick@wg0`). Прежние версии писали метку
времени в рукопожатии не тем порядком байт, а сервер помнит самую большую из принятых меток и,
пока не перезапущен, считает новые (правильные) инициации повтором.

### 6. Разделение трафика

- **По приложениям:** всё через туннель, только выбранные, всё кроме выбранных.
- **По адресам:** весь трафик, встроенные наборы, списки allow-domains или свои CIDR.
  Списки скачиваются из источника, разворачиваются в маршруты и используются в `AllowedIPs`.
- **YouTube при «только часть сайтов»** (с 1.10.33): видео идёт с серверов googlevideo.com, их
  адреса выдаются под каждое видео, и заранее в список их не внести. Если YouTube в туннеле
  (отмечен его список, выбрано приложение или он есть в своих сайтах), к маршрутам при
  подключении сами добавляются сети Google, откуда идёт видео.
- **Маршруты всегда текущие** (с 1.10.33): с какой бы точки ни поднимался туннель — из топа, из
  очереди, после обновления или перезагрузки, — маршруты берутся из «Туннелирования», а не из
  конфига, сохранённого при подборе.

- **Браузер — только к нужным сайтам** (с 1.10.35, переключатель в «Туннелировании» →
  «Приложения», включён). Android сначала решает по приложению: приложение вне туннеля до него не
  доходит, какие бы сайты ни были выбраны. А адреса у туннеля общие для всех выбранных приложений.
  Поэтому, если среди выбранных есть браузер, маршруты — не «весь трафик», а сайты второго выхода
  (ChatGPT, Claude, Gemini, заблокированные для РФ — их сервис добавляет сам), «Мои сайты» и
  отмеченные списки плюс сети выбранных приложений. Telegram, Instagram, Facebook, WhatsApp,
  YouTube, X, Discord, ChatGPT, Claude, Gemini ходят только в свои сети и идут через туннель
  целиком; из браузера через туннель идут только эти сайты (и сайты тех же сервисов: youtube.com,
  instagram.com), остальное — напрямую. Приложения, чьих сетей приложение не знает, при этом идут
  только к выбранным сайтам — об этом предупреждает сводка «Сейчас через туннель». Браузер узнаётся
  по тому, что открывает любую ссылку https.
- **Сети выбранных приложений — сами** (с 1.10.35): и в режимах «сайты из списков» и «мои сайты»
  выбранные Telegram, Instagram, YouTube и другие известные приложения идут целиком — их сети
  добавляются к маршрутам. Раньше без отмеченного списка Telegram шёл «мимо туннеля».
- **Поддомены второго выхода** (с 1.10.35): в списках allow-domains — правила «домен и все
  поддомены», а приложение превращает в адреса ровно перечисленные имена. Вход в ChatGPT живёт на
  auth.openai.com, которого в списке нет, — он уходил через WARP с российским адресом
  («unsupported_country_region_territory»). Теперь поддомены ChatGPT, Claude и Gemini добавляются
  сами, а адреса после обновления собираются заново, не дожидаясь суток.
- **Gemini — вместе с приложением Google** (с 1.10.37). Gemini на Android — оболочка в несколько
  мегабайт: запросы к Google, и проверку страны тоже, делает приложение Google. Отмеченный Gemini
  без него писал «Эта страна не поддерживается»: второй выход работал, но приложение Google в туннель
  не входило, и запросы шли мимо, с российского адреса оператора. Теперь в режиме «только выбранные»
  приложение Google идёт через туннель вместе с Gemini само (в списке у Gemini подпись «с ним пойдёт
  приложение Google»). Сетей ему не добавляется: при «весь трафик» всё приложение Google идёт через
  WARP, а адреса Gemini — через второй выход; при неполных маршрутах из него через туннель идут только
  сайты Gemini и другие выбранные, остальное — напрямую. Если Gemini и после этого пишет «страна не
  поддерживается», он помнит прежний ответ: остановите приложение Google («Настройки → Приложения →
  Google → Остановить») и очистите данные Gemini.

### 7. Выход WARP в России (с 1.10.34)

WARP выходит в интернет через площадку Cloudflare, которую выбирает маршрут оператора: `HEL` —
Хельсинки, `DME` — Москва. Через московскую площадку трафик попадает под российские фильтры: с
2026 года так замедляют медиа Telegram («соединение быстрое, а фото и видео грузятся рывками»).
Одна и та же точка на разных сетях и в разное время может выходить через разные площадки, но
разные подсети Cloudflare приходят на разные площадки, поэтому:

- **Подбор узнаёт площадку каждой точки** — запросом `id.server` к 1.1.1.1 внутри той же пробы
  данных — и ставит выход за рубежом выше московского (в баллах, в тройке каждой сети и в
  перебор при обрыве). Если на сети за рубежом не выходит ни одна точка, так и пишется в журнал.
- **Поиск выхода за рубежом сам** (переключатель в «Автоматике»): если проверка связи показала
  выход в России, приложение ищет точку с выходом за рубежом — только на зарядке с погашенным
  экраном (5 минут), не чаще раза в сутки на сеть. Туннель гаснет на минуту-две и возвращается сам,
  а включённый экран прерывает поиск сразу.
- **Telegram — через второй выход только по вашему ответу** (с 1.10.36; переключатель «Telegram:
  предлагать второй выход» в «Автоматике»). Telegram идёт через выход WARP, даже если он в Москве:
  режут там не всегда, а второй выход бывает медленнее. Если проверка медиа через Москву показала
  «тормозит», та же загрузка идёт через второй выход, и если он заметно быстрее, приходит
  уведомление с цифрами: «Через Москву: 300 Кбит/с, медленно. Через второй выход (Нидерланды):
  4,1 Мбит/с. Переключить Telegram?» — кнопки «Переключить» и «Оставить». Ответ действует сутки для
  этой сети; без ответа приложение не спрашивает снова три часа. После «Переключить» приложение
  меряет оба пути и, если второй выход стал медленнее Москвы, само возвращает Telegram через WARP
  (строка в журнале). Если уведомления выключены, тот же вопрос задаёт окно на открытом экране.
  Переключение — на лету, без переподключения; при замере отдельно переводится только адрес
  загрузки, живые соединения Telegram не рвутся. Нужен настроенный второй выход (свой сервер или
  Proton Free). Если Telegram идёт мимо туннеля по выбранным маршрутам, его это не касается.
- **На экране** выход по-прежнему страной («выход: RU»), а при выходе через Россию — городом и с
  предупреждением: «выход: Москва — Telegram может тормозить» (или «… — Telegram через второй
  выход», когда он и правда поднят).
- **Проверочные подъёмы подбора не запоминаются** как «работающая точка»: раньше после подбора
  туннель мог подняться на точке, через которую данные не шли.
- **При неполных маршрутах выход тоже виден** (с 1.10.35): проверка связи идёт к 1.1.1.1, который в
  туннеле и при «сайтах из списков» (DNS идёт через туннель). Раньше она писала «интернет — мимо
  туннеля» и не видела, через какой город выходит WARP.

## Что и как часто

| Что происходит | Как часто | Зачем |
|---|---|---|
| keepalive | 25 с (по настройке), не чаще 60 с при живом экране, не чаще 90 с в тишине с погашенным экраном, максимум 120 с | держать NAT-таблицу и сессию живыми |
| пересогласование сессии (rekey) | каждые 150 с при трафике; повтор через 5 с | протокол требует успеть до 180 с |
| попытка handshake | 4 инициации с интервалом 450 мс | первая датаграмма на мобильной сети теряется |
| проверка «а жива ли сессия» | на каждом отправленном пакете, без таймеров | заметить мёртвую сессию за секунды, а не за минуты |
| строка статистики в журнале | раз в 5 минут (в глубоком сне реже — тогда пишется настоящая длина интервала) | видно, что именно расходует батарею |
| определение региона выхода | один раз после подъёма | показать, куда ведёт туннель |
| проверка медиа Telegram | при проверке связи, если экран включён: не чаще раза в 30 минут или при смене площадки, до 256 КБ; если через Москву тормозит — ещё раз через второй выход (а после «Переключить» — оба пути), до 512 КБ | увидеть «связь есть, медиа тормозит» и понять, поможет ли второй выход |
| поиск выхода за рубежом | выход в России, зарядка, экран погашен 5 минут — не чаще раза в сутки на сеть | уйти с московской площадки без нажатий |
| проверки сайтов | при подборе и по кнопке «Проверить» | «открывается» вместо «наверное, работает» |
| фоновый подбор | выключен по умолчанию; 6–12 часов, если включить | обновить точку, когда сеть изменилась |
| смена точки входа | при обрыве: сразу следующая из очереди, до 6 подряд; не ответила ни одна — новый круг через 30 с, 1, 2, затем 5 мин | подняться без ручного нажатия |
| попытка при включении экрана | только когда туннель лежит и ждёт повтора; не чаще раза в 30 с | не ждать паузы, когда человек смотрит на телефон |
| дозор очереди перебора | раз в 12 минут при поднятом туннеле (первый — через 3 минуты): 2 точки, 1–2 инициации на каждую | при обрыве сразу перейти на живую точку |

## Куда обращается приложение

| Адрес | Что это | Когда используется |
|---|---|---|
| `162.159.192.*`, `162.159.195.*`, `188.114.96–99.*`, `8.*.*.*` Cloudflare | точки входа WARP, UDP | подбор, подключение и дозор очереди перебора |
| `engage.cloudflareclient.com:2408` | тот же WARP, по имени | как обычная точка |
| зеркала `warp-api.cfd` | выдача ключей WARP | первый запуск и обновление аккаунта |
| `cloudflare-dns.com/dns-query`, `dns.google/resolve` | DoH | сборка адресов для второго выхода, сверка DNS |
| проверяемые сайты (см. список выше) | HTTP(S)-запросы | проверки при подборе и по кнопке |
| `cloudflare.com/cdn-cgi/trace` | регион и признак `warp=on` | после подъёма туннеля |
| `speed.cloudflare.com` | замер скорости | по кнопке в отчёте |
| `1.1.1.1` (запрос `id.server` внутри пробы WARP) | площадка выхода точки | подбор |
| `telegram.org` (начало `/dl/android/apk`, до 256 КБ) | проверка медиа Telegram | проверка связи, не чаще раза в 30 минут |

Приложение не создаёт аккаунтов, не собирает телеметрию, не показывает рекламу и не отправляет
никуда ничего, кроме перечисленных запросов. Ключи, конфиги и журналы лежат в приватном каталоге
приложения; приватный ключ дополнительно шифруется ключом из Android Keystore.

## Батарея

| Состояние | Расход |
|---|---|
| приложение закрыто, туннель выключен | практически ноль: нет wakelock, нет будильников, фоновый подбор выключен |
| туннель поднят, экран погашен, Wi-Fi | около 1 % в час (измерено: 4 % за 94 минуты при 48–150 мА, модем 0 Б) |
| туннель поднят, экран погашен, мобильная сеть | 1–3 % в час: пробуждение радиомодуля дороже самого пакета |
| туннель поднят, телефон в работе | меньше, чем расходует сам экран |
| подбор конфигурации | обычный скан — единицы процентов; полный перебор — десятки: минуты непрерывной работы радио |

Проверить это можно по журналу: строка `статистика:` раз в 5 минут показывает keepalive,
рукопожатия, байты вверх/вниз, секунды без трафика, процессорное время по потокам,
переподключения, смены сети, заряд, ток, израсходованные мА·ч и трафик модема. По ней видно, что
именно ело батарею — процессор при малом трафике, частые переподключения или сам модем.

## Требования и установка

- Android 8.0 и новее.
- При первом подключении система спросит разрешение на VPN — без него туннель не поднимется.
- Для «только выбранные / всё кроме выбранных» отдельного разрешения не нужно: с 1.10.32 приложение
  видит только приложения с иконкой на рабочем столе (а не весь список пакетов) — их и показывает.
- Ставить другие приложения WarpScout не может: разрешения «Установка приложений» у него нет (в
  1.10.31 оно было для кнопки «Обновления», и «Защита приложений» Samsung на движке McAfee из-за него
  называла APK вредоносным).

Установка APK из файла: разрешите «Установка неизвестных приложений» для файлового менеджера или
браузера, которым открываете файл. Обновление ставится поверх предыдущей версии: настройки, ключи
и подобранный конфиг сохраняются. Кнопка «Обновления» в приложении скачивает новую версию в
«Загрузки»; поставить — нажатием на файл или на уведомление «Загрузка завершена».

## Релизы

Готовые APK — в разделе [Releases](../../releases). В каждом релизе два файла:

| Сборка | Что внутри | Application ID |
|---|---|---|
| `WarpScout-<версия>-tunnel.apk` | полное приложение со своим туннелем; открывается упрощённым экраном | `dev.warpscout.app.tunnel` |
| `WarpScout-<версия>-scout.apk` | то же приложение; открывается расширенным экраном со всеми вкладками | `dev.warpscout.app` |

- С 1.10.27 сборки различаются только видом экрана при первом запуске: «только конфиги» больше
  нет, туннель есть в обеих. Вид меняется тумблером внизу экрана и запоминается.
- Обе сборки можно держать на телефоне одновременно: идентификаторы различаются (но VPN в Android
  одновременно работает только один).
- Сборки **debug-подписанные**: годятся для сайдлоада и тестов, не для магазина приложений.
- Контрольные суммы SHA-256 лежат в том же релизе (`SHA256SUMS.txt`).
- Предыдущие версии остаются на странице релизов (с 1.10.30 старые релизы не удаляются;
  1.10.24–1.10.26 восстановлены из исходных сборок). Вернуться на более старую версию можно, только
  удалив текущую: поверх новой Android старую не ставит, а настройки при удалении сотрутся.

## Сборка из исходников

```bash
git clone https://github.com/kos19191/warp-scout-src
cd warp-scout-src

./gradlew :app:assembleTunnelDebug      # открывается упрощённым экраном
./gradlew :app:assembleScoutDebug       # то же, открывается расширенным экраном
./gradlew :core:check                   # самопроверка протокольного слоя
```

Нужны JDK 17 и Android SDK (compileSdk 35). Для релизной подписи — `app/release.keystore` и
переменные `WARPSCOUT_STOREPASS`, `WARPSCOUT_KEYALIAS`, `WARPSCOUT_KEYPASS`; без них используется
debug-ключ.

```
core/   протокольный слой: WireGuard/AmneziaWG, криптография, подбор, маршруты, списки
app/    Android-приложение: экраны, VpnService, настройки, экспорт
cli/    консольный вариант подбора (без Android)
tools/  оффлайн-проверки для CI
```

```bash
./gradlew :cli:installDist
./build/install/cli/bin/cli tune --profiles 4 --count 200
```

**Проверки в CI:** `tools/android_stub_check.py` (ресурсы и разметка без SDK), самопроверка
протокольного слоя (`SelfCheck`: криптография, handshake, разбор конфигов, маршрутизация),
векторы фейкового WARP-сервера на независимой реализации на Python, интеграционный прогон
«наш клиент против Python-сервера», сборка обеих APK.
