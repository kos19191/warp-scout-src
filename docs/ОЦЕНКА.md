# WarpScout: оценка кода и конкретные предложения

Дата: 19.11.2026. Оценка по коду ветки `arena/51ec8e2b-warp-scout-src` (после правок этого цикла),
сборке APK и прогону самопроверок в CI. Цифры и утверждения ниже проверяемы: каждая проблема
указывает файл, а не «ощущение».

---

## 1. Что за проект и как он устроен

Android-приложение + CLI на Kotlin для подбора рабочей конфигурации Cloudflare WARP:

```
core/   ядро без Android: crypto (BLAKE2s, X25519, ChaCha20-Poly1305), WireGuard-сообщения,
        data plane поверх VpnService/tun, генератор ключей, пул endpoint'ов, пробы,
        пресеты (шум, DNS, маршруты), подбор (AutoTuner), отчёты, самопроверки
cli/    тот же core в терминале: scan / gen / tune / selftest
app/    один экран: настройки → «Сканировать и подобрать» → конфиг/файл/туннель
        два flavor'а: scout (без туннеля) и tunnel (со своим VpnService)
```

Главное архитектурное достоинство: **core не знает про Android**. Поэтому один и тот же код
крутится в APK, в CLI и в CI, а протокольный слой проверяется офлайн-векторами.

## 2. Сильные стороны (то, что не надо трогать)

1. **Реальные вердикты, а не пинги.** Кандидат считается живым, только если сервер WireGuard
   принял именно наш ключ (`WgProber` → handshake). Пинг до IP не значит ничего: у Cloudflare
   любой адрес отвечает ICMP.
2. **Один data plane для тестов и для туннеля.** `DataPlane` гоняет те же пакеты, что и `WarpVpnService`:
   «работает в тесте» и «работает в туннеле» — это один и тот же код.
3. **Самопроверки вместо надежды.** `:core:selftest` — сотни проверок: BLAKE2s/X25519/ChaCha
   на векторах, разбор и рендер конфигов (round-trip), схлопывание CIDR, отчёты, плюс
   интеграция с Python-эмулятором WG-сервера. Это редкая роскошь для Android-проекта.
4. **Честные ошибки в отчёте.** Балл складывается из RTT/джиттера/потерь и проверок ресурсов,
   а не из «сколько портов открыто»; конфиг, не прошедший handshake, в отчёт не попадает.
5. **Ноль сетевой телеметрии.** Всё считается локально; наружу уходят только запросы, которые
   и так нужны для проверки (handshake, HTTPS, DoH).
6. **Разделение flavor'ов.** `scout` без VPN-разрешений — можно ставить «сканер» отдельно и не
   пугать пользователя запросом на перехват трафика.

## 3. Проблемы по приоритетам

### P0 — «туннель запускается и ничего не происходит» (исправлено в этой ветке)

Симптом воспроизводился по коду и имел **четыре независимые причины**:

| Причина | Что было | Что стало |
|---|---|---|
| ANR на main-потоке | `onStartCommand` синхронно ждал handshake до 12 с | поднятие вынесено в отдельный поток |
| Причина падения затиралась | после ошибки `stopSelf()` → `shutdown()` писал «туннель остановлен» поверх «handshake не прошёл» | `TunnelState.error` живёт до следующего запуска, коды `E_CONFIG/E_SOCKET/E_PROTECT/E_TUN/E_HANDSHAKE/E_FGS/E_REVOKE/E_CRASH` |
| Разрешение выдано — и тишина | после `VpnService.prepare` никто не продолжал запуск | `ActivityResultLauncher` → сразу `launchTunnel()` |
| Нет обратной связи | статус обновлялся только по нажатию | строка состояния раз в секунду (этап + ↑↓ трафик), кнопки «Проверить туннель» и «Журнал» |

Плюс закрыты дыры, которые ждали своего пользователя: `onRevoke()` (отзыв VPN другим
приложением оставлял «мёртвый, но включённый» туннель), `setUnderlyingNetworks()` (переключение
Wi-Fi↔LTE), сброс `stopped` при повторном старте, `startForegroundService` больше не глотается
молча.

### P0 — проглоченные ошибки

В коде 122 `runCatching` и 11 `getOrDefault`, часть — без единой записи в журнал
(`KeyVault.load()`, `ConfigFiles.write`, `Report.writeAll`, `CleanNetwork.*`). Для пользователя это
выглядит как «ничего не произошло», для разработчика — как «воспроизведите у себя».

Предложение: правило «`runCatching` без `.onFailure { … }` — ошибка линта». Минимум — писать
в `TunnelDiagnostics`/лог подбора, а не возвращать `false`/`null` молча. Это дешёвая правка,
и она окупается на первом же баг-репорте.

### P1 — генератор ключей зависит от чужого зеркала

`KeySource` ходит на пять хостов `*.warp-api.cfd` (третья сторона, не Cloudflare). Если зеркало
умрёт или начнёт отдавать чужое — приложение не сможет подобрать конфиг, а приватный ключ
пройдёт через чужой сервер.

Предложения:
1. Официальная регистрация WARP через `https://api.cloudflare.com/client/v4/reg` (нужен
   `tos`/`accepted_at`, ключ генерируется локально) — но она требует аккаунта/токена, поэтому
   только как «ручной импорт».
2. Локальная генерация: приватный ключ создаём сами (X25519 уже есть), а у зеркала просим только
   адрес — это снижает ущерб от компрометации зеркала до «узнают публичный ключ».
3. Помечать в UI источник ключей (уже показывается) и предупреждать, если использовано зеркало.

### P1 — нет обычных unit-тестов

Самопроверки — это интеграционные штуки с `println`; JUnit нет ни в `core`, ни в `app`. Любая
правка `SplitTunnel`/`Cidr` проверяется только глазами.

Предложение: `src/test/kotlin` в `core` + JUnit 5, перенести туда чистые проверки
(схлопывание CIDR, разбор конфигов, скоринг, отчёты), оставив в `selftest` только сетевые и
дорогие. CI получит `:core:test` за секунды вместо минуты.

### P1 — состояние экрана живёт в Activity

`MainActivity` — 700+ строк, экран один, но состояние размазано по 15 полям (`log`,
`cancelled`, `runStartedAt`, `endpointBeforeRun`, `lastConfigFile`, `pendingTunnelConfig`, …).
Разметка — 512 строк в одном файле, без `ViewModel`: поворот экрана пересоздаёт всё, лог
подбора теряется, а подбор продолжается (что хорошо) — но UI об этом не знает.

Предложение: `MainViewModel` + `StateFlow<UiState>`, разметка на `FragmentContainerView` или
хотя бы `include`-блоки. Побочный эффект: `WorkManager` и Activity начнут читать одно состояние,
а не два разных.

### P1 — Clash-экспорт без `rules` (исправлено в этой ветке)

Было: `ConfigExport.clashYaml()` отдавал только `proxies:`. Clash Meta такой файл принимает, но
не применяет: без `proxy-groups`/`rules` трафик идёт напрямую — классическое «импортировал, а не
работает».

Стало: полный минимальный конфиг — `mixed-port`, `mode: rule`, `dns`, `proxies` (с
`amnezia-wg-option`), `proxy-groups: [{name: WARP, type: select}]`, `rules: [MATCH,WARP]`.
Плюс исправлен разбор `allowed-ips`: после запятой каждый CIDR обрезается, иначе `" ::/0"` не
является подсетью и Clash ругается на конфиг. В `SelfCheck` появились пять проверок на это.

### P2 — 48–64 параллельных пробы на телефоне

`NetSettings.concurrency = 48` по умолчанию, у тюнера — 64. На LTE это десятки сокетов и
постоянные wakeup'и: греется батарея, оператор может начать резать.

Предложение: гейт по типу сети (`ConnectivityManager.getNetworkCapabilities`: Wi-Fi → 64,
LTE/5G → 24, «экономный режим» → 8) и по заряду (`BatteryManager`, < 15% — вдвое меньше).
Плюс `setThreadPriority(THREAD_PRIORITY_BACKGROUND)` в пуле.

### P2 — нет кэша результатов скана

Каждый запуск заново перебирает пул, хотя «эти 40 endpoint'ов отвечали 10 минут назад» —
валидное знание. `prefs.lastTunedEndpoint` хранит только один.

Предложение: `scan-cache.json` в `filesDir` (endpoint → lastOk, rtt, время), TTL 30–60 минут,
в тюнер — сначала кандидаты из кэша, потом новые. Экономит самый дорогой этап.

### P2 — `Thread.sleep` вместо дедлайнов

8 мест, где поток спит фиксированные миллисекунды. На медленной сети это либо слишком рано
(и проверка врёт), либо слишком поздно (и подбор ползёт).

Предложение: `await` по условию с дедлайном, как уже сделано в `startAndWait`.

### P2 — DNS и IPv6 в частичных режимах

В режимах «только выбранные категории» и «только заблокированное» добавлен маршрут на
`1.1.1.1/32` — без него DoH-запросы утекают мимо туннеля. Но системный резолвер может ходить
на DNS оператора, если в конфиге `dns` не переопределён в `tun`.

Предложение: в этих режимах принудительно ставить `dns = [1.1.1.1]` и `addDnsServer` (сейчас так
и делается, но выбор DNS в настройках может это перебить — нужно предупреждение в UI).

### P2 — нет `StrictMode` и baseline-профилей

Дисковые операции в UI-потоке (`Prefs` в `onCreate`, `ConfigFiles.dir`) сейчас не видны.
`StrictMode` в debug-сборке ловит их мгновенно и бесплатно; baseline-профиль (Macrobenchmark
или `androidx.profileinstaller`) убирает jank на старте.

### P3 — мелочи, которые видно пользователю

* Нет индикации «сколько ещё ждать» — прогресс идёт строками, а не процентами с ETA.
* «Передать в AmneziaVPN» — на самом деле кладёт в буфер + открывает «Поделиться»: подпись врёт.
* Дата снапшота списков показывается только в диалоге категорий — стоит вынести в «О приложении».
* Нет «Скопировать журнал» одной кнопкой (сейчас — через диалог).

## 5. Оптимизации с конкретикой

1. **Меньше сокетов — больше скорости.** `WgProber` создаёт по сокету на пробу. Один
   `DatagramChannel` в неблокирующем режиме + `Selector` на 200–500 «проб» даёт тот же результат
   без 48 потоков: экономия — десятки МБ RSS и заметный минус к нагреву.
2. **`SocketUdpChannel` → `DatagramChannel`** в data plane: `receive()` с таймаутом 1500 мс
   просыпается впустую 99% времени; неблокирующий канал с `Selector` снижает латентность
   туннеля на 1–3 мс и убирает пустые wakeup'и.
3. **Кэш DoH-ответов** (TTL 10 мин) — в режиме «только выбранные категории» резолв занимает
   секунды на каждом запуске подбора, а домены те же.
4. **Снапшот в APK**: 68 КБ — не проблема, но `RuleData` читает файлы целиком в память при каждом
   запросе. Стоит закешировать `lazy` по id (сейчас читается 1–2 раза за запуск — низкий приоритет).
5. **R8 + `isShrinkResources`** в release: сейчас APK 18 МБ в debug; release с R8 обычно даёт
   −40–50% без риска (ядро рефлексии не использует).
6. **Baseline profile** на «нажал Сканировать» — убирает первый провал кадров при заполнении лога.

## 6. Дорожная карта

1. **Сейчас (эта ветка):** туннель + формат конфига + списки + отчёт.
2. **Следующий шаг:** JUnit для `core` (перенос чистых самопроверок), линт-правило на
   `runCatching` без обработки, подсчёт ETA в прогрессе подбора.
3. **Потом:** `ViewModel` + `StateFlow`, гейт конкурентности по сети/батарее, кэш сканов,
   `DatagramChannel`+`Selector`.
4. **Отдельная задача:** независимость от `warp-api.cfd` (локальная генерация ключей,
   официальная регистрация как опция).

## 7. Как это проверять самому

```bash
./gradlew :core:selftest          # офлайн: крипто, конфиги, CIDR, split-tunnel, отчёты
./gradlew :cli:run --args="scan --count 20"        # живая сеть
python3 tools/fake_warp_endpoint.py --selftest     # эмулятор WG-сервера
./gradlew :app:assembleTunnelDebug                 # APK со своим туннелем
```

Самопроверки — это страховка: они ловят поломку протокола и форматов без телефона. Всё, что не
ловится ими (туннель на устройстве, UI), нужно проверять на APK — и именно там теперь есть журнал,
который можно прислать вместо «не работает».
