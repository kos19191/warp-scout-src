# Обход DPI на Android: ByeDPI (и GoodbyDPI на ПК)

Снапшот фактов, на которые опирается реализация. Проверено по репозиторию
[dovecoteescapee/ByeDPIAndroid](https://github.com/dovecoteescapee/ByeDPIAndroid)
(ветка `master`, последний коммит — 5 сентября 2024, 50 коммитов) и по README проекта.

## Что это

* Приложение поднимает **локальный SOCKS5-прокси** на базе ядра
  [hufrea/byedpi](https://github.com/hufrea/byedpi) и перенаправляет через него трафик
  (формулировка из README: «Приложение локально запускает SOCKS5-прокси ByeDPI и перенаправляет
  весь трафик через него»).
* Транспорт между приложением и прокси — `hev-socks5-tunnel` (раньше был `tun2socks`),
  то есть используется Android VPN-API, но **на удалённый сервер ничего не уходит**:
  «Это VPN? Нет. Приложение использует VPN-режим на Android для перенаправления трафика,
  но не передает ничего на удаленный сервер. Оно не шифрует трафик и не скрывает ваш IP».
* Root не нужен («Все функции приложения работают без root-прав»).
* Прокси по умолчанию — `127.0.0.1:1080`. В README есть сценарий «Запустите ByeDPI в режиме прокси»
  и пример, как на этот порт подключить другое приложение (AdGuard: «Тип прокси: SOCKS5, Хост:
  127.0.0.1, Порт: 1080»). Именно этот режим мы и используем для сравнения.
* Настройки обхода (фрагментация, фейные пакеты, TTL, `split position`, TCP Fast Open, UDP fake
  count) живут в UI ByeDPI и описаны в документации ядра — наш код их не дублирует.

## Почему WarpScout не повторяет эти трюки сам

GoodbyDPI/ByeDPI переписывают сами TCP-сегменты: фрагментируют заголовок, ставят несуществующий
`Seq/Ack`, TTL, отправляют фейные пакеты «от имени» обеих сторон. В обычном сокет-API Android для
этого нет рук: `java.net.Socket` не даёт ни фрагментацию TCP, ни `IP_TTL`, ни raw-сокеты (raw —
только root). ByeDPI это и делает userspace-стеком на C поверх tun, а не настройкой сокета.

Поэтому у нас два осмысленных сценария, и оба реализованы:

1. **Измерить, что меняет обход DPI.** `core/dpi/DpiComparator.kt` гоняет один и тот же список
   ресурсов напрямую и через SOCKS5 `127.0.0.1:1080`, и по разнице ставит вердикт:

   | результат | что это значит | чем лечится |
   |---|---|---|
   | открыто и там и там | блокировки нет | ничего |
   | лежит напрямую, открывается через ByeDPI | блокировка **DPI-образная** | настройки ByeDPI (frag/split/fake) |
   | напрямую работает, через ByeDPI нет | мешают настройки обхода | отключить часть флагов в ByeDPI |
   | не открывается ни так, ни так | блокировка **по IP/маршруту** | подобранный endpoint WARP |

   Если SOCKS5 не отвечает, вердикт — `PROXY_UNREACHABLE`: приложение не будет врать про
   «блокировки», когда просто не запущен прокси.

2. **Мерить базу через обход.** Галочка «Гонять базовые замеры через ByeDPI» (`tuneViaByedpi`)
   пропускает TLS-пробы MASQUE и HTTP-проверки ресурсов через `Socks5Endpoint`
   (`NetSettings.socks5`, `HttpClient(proxy=...)`), чтобы подбор стартовал с честной картины.
   UDP-хэндшейк WireGuard через SOCKS5 не пушится (SOCKS5 — это TCP), поэтому пробы endpoint'ов
   всегда идут напрямую.

## Важное ограничение: два VPN одновременно

Android держит один активный `VpnService`. Значит «ByeDPI в режиме VPN» и наш встроенный туннель
(`WarpScout-tunnel`) одновременно не работают — приложение об этом пишет прямым текстом в секции
ByeDPI. Рабочие комбинации:

* **только ByeDPI** (режим VPN) — если блокировка оказалась DPI-образной;
* **только наш туннель / Amnezia** — если блокировка по IP, тогда обход DPI не помогает в принципе;
* **ByeDPI в режиме прокси + наш подбор** — базовые замеры и TLS-пробы идут через обход,
  UDP-пробы endpoint'ов напрямую; так и задумано.

Отдельно: WireGuard-туннель сам по себе шифрует трафик, и DPI внутри туннеля уже ничего не видит.
Трюки обхода DPI нужны ровно для того, что остаётся **снаружи**: для базовых проверок «открыто ли
это у провайдера» и для случаев, когда блокируют не ресурс, а сам WireGuard-эндпоинт.

## Как проверить без телефона

Сравнение закрыто офлайн-тестами ядра, сети им не нужны:

```
./gradlew :cli:selftest        # секция «socks5 / сравнение с ByeDPI»
```

Там поднимаются фейковый HTTP-источник, фейковый SOCKS5-релей (с подменой домена
`blocked.invalid`, который в реальности не резолвится никогда — RFC 6761) и фейковый «прокси с
аутентификацией». Проверяются: байты рукопожатия (`05 01 00` → `05 00`, `CMD=CONNECT`,
`ATYPE=1`, порт в сетевом порядке), релей трафика, четыре вердикта компаратора и то, что при
мёртвом прокси он **не** заявляет блокировки.
